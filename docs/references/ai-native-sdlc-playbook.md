## 1. Thesis

- AI now writes code faster than the surrounding process can absorb. The approval gates,
  reviews, handoffs and policies haven't changed, and they stall the productivity gains.
- The traditional SDLC was optimised for an era when writing code was the expensive step.
  PRDs, estimation rituals and security reviews existed to force alignment across long
  build cycles.
- Once build collapses to hours, three things follow:
  1. The bottleneck moves to the steps before and after build: plan, review/test and deploy.
  2. Controls stop matching reality. Line-by-line human review can't keep up when agents
     write most of the diff.
  3. Governance costs rise, because exceptions still go through weekly or monthly committees.
- Example: security teams are sized for human output. Either the review queue grows or code
  ships under-reviewed, and a regulated organisation can accept neither.

> "Build is no longer the constraint — the human-speed steps around it are."

## 2. What an AI-native SDLC is

- It keeps the old **control objectives** but enforces them in new ways.
- A **loop instead of a linear flow**, with AI at every stage. Handover between stages is
  automated, and each stage triggers the next.
- It is also called the agentic SDLC, the AI SDLC or agentic software development.
- **Each stage ends by committing an artifact to version control, and the next stage begins
  by reading it.** Early stages use `.md` files, which a product owner and an agent can both
  read. From Build onwards, the artifact is code and its records.
- The chain of commits is the audit trail: who asked for what, what the agent produced, and
  who approved it.
- Humans stay accountable for every decision that needs judgment. Their attention moves to
  reviewing the artifacts.

> "Every stage commits an artifact the next stage can read."

### Traditional vs AI-native (most organisations sit somewhere between)

| Stage | Traditional | AI-native |
|---|---|---|
| Plan | Requirements gathered by committee, through workshops and sign-offs, written up by hand | Claude synthesises pain points from the sources into `intent.md`, which is both human-readable and machine-actionable |
| Design | Analysts write the spec; designers parse it | Requirements and design in one session with an agent, guided by standards encoded as skills, versioned in git |
| Build | Tests and code handwritten; documentation written afterwards | Tests and code generated by AI; institutional knowledge kept in versioned CLAUDE.md files and skills |
| Test | **QA gates at stage boundaries** | **Continuous evals woven through implementation** |
| Deploy | Humans review every line; governance in review cycles, often inconsistent | Layers of agentic review, with human review reserved for regulated and critical code; governance enforced as the AI acts, with hooks as approval gates |
| Maintain | Humans watch production for bugs | Agents monitor live deployments; any breached control band is diagnosed and written back into the loop as a new `intent.md` |

### The artifact chain and its triggers

```
idea / ticket / alert
   └─> intent.md      (accepted by PO)            ──triggers──> requirements & design pass
         └─> spec.md  (approved by PO)             ──triggers──> plan mode
               └─> plan.md (accepted by engineer) ──> implementation: diff + tests
                     └─> PR + review findings (merged) ──triggers──> pipeline / deploy
                           └─> production; a breached control band writes the next intent.md ──┐
   ^────────────────────────────────────────────────────────────────────────────────────────┘
```

Rollout pattern: **prompt each step by hand first**. The end state is a loop where each
accepted artifact fires the next gate, and people review what the agent flagged instead of
starting each stage from scratch.

## 3. How each play is structured

The playbook calls its practices "plays". Each one covers: what changes, getting started
(**prerequisites** and **infrastructure**), how to execute it, governance considerations,
and how to measure it (a **leading** and a **lagging** indicator). The plays are modular, and
organisations can transform stages in any order. Adoption order follows the prerequisites,
not the stage order. Plays with no prerequisites can be adopted first.

## 4. The plays, stage by stage

### Stage 1: Plan

#### Play: Capture as intent.md
- **What changes:** intent enters through an idea, a ticket or an incident alert. The
  originator brainstorms with Claude, which asks the questions an analyst would ask: scope,
  users, constraints and what success looks like. The result is a markdown proto-spec,
  `intent.md`, in the originator's own words. It replaces the traditional path of backlog
  entries, user stories, story points and refinement meetings, where ownership changes hands
  at each step.
- **Template sections in the example:** author and status; Problem; Proposed outcome;
  Affected users and systems; Constraints; Open questions. The template can be encoded as a
  skill that a lead signs off.
- **Prerequisites:** none.
- **Infrastructure:**
  - Claude access for non-engineers (claude.ai or Cowork).
  - An agreed template.
  - A version-controlled "intent home" that the PO watches. The simplest is an `intent/`
    folder in the product repo. A dedicated repo is only worth it if intent spans many repos.
  - A connector to version control, so non-git users can commit through Claude.
- **Governance:**
  - The committed file records the author, timestamp and revision history.
  - **The PO reviews and corrects the agent-written intent before it is committed.**
  - The PO's accept or reject decision is recorded as the merge or the closed review.
- **Leading indicator:** time from first conversation to a committed intent.md, expected to
  fall from weeks to hours.
- **Lagging indicator:** the survival rate, meaning the share of intents accepted into
  Design. Also, the number of intent.md edits made after the first spec.md commit.

### Stage 2: Design

#### Play: Requirements and design
- **What changes:** Claude turns an accepted intent.md into a requirements and design spec,
  `spec.md`. It is constrained by the organisation's skills for brand, security, compliance
  and UX, and it **flags areas of concern**. The PO reviews the spec but doesn't write it.
  For front-end work, the PO can mock the design in Claude Design (beta) and export it to
  Claude Code.
- **Prerequisites:** an intent.md, and brand, security, compliance and UX policies written
  as skills.
- **Infrastructure:** a PO with Claude access. No engineering skill is needed.
- **Execution:**
  1. Run the pass by hand at first.
  2. Codify it as an organisation-level slash command.
  3. Finally, make the merge of intent.md trigger a non-interactive job that commits spec.md
     as a PR.
  4. Resolve flagged concerns with the named policy owners before engineering sees the spec.
  5. Commit spec.md next to intent.md.
- **Governance:**
  - Policy is applied while the spec is written, not discovered in review weeks later.
  - The spec, the prompt and the skill versions in force are all versioned.
  - **A human always decides whether the spec goes to build**, consulting a tech lead for
    higher-risk work.
- **Leading indicator:** time from the intent.md commit to the spec.md commit.
- **Lagging indicator:** requirements rework, meaning spec.md commits dated after the first
  plan.md commit.

### Stage 3: Build

> "Nothing is implemented without an accepted plan."

#### Play: Plan mode as the default starting point
- **What changes:** the engineer starts in plan mode with spec.md, and Claude interviews the
  engineer. The plan names **the files that change, the order of work, and the tests that
  prove it**. The engineer then challenges the plan: what could it break, which step is most
  risky, and which alternatives did Claude reject? Iterate until someone who never saw the
  conversation could implement from the plan alone. Commit it as `plan.md`.
- **Example plan.md sections:** Files that change; Order of work; Risks; **Proof** (the tests
  and screenshot checks that show it works).
- **Prerequisites:** intent.md or spec.md if one exists; a CLAUDE.md helps.
- **Governance:**
  - Design review happens before any code exists.
  - Plan mode enforces this, because Claude can't edit until the plan is accepted.
  - The engineer approves routine plans; a tech lead or architect approves higher-risk ones.
  - When implementation departs from the plan, update plan.md in the same commit. A hook can
    enforce this.
- **Leading indicator:** share of changes that merge from the first pass; time from plan
  approval to merged PR.
- **Lagging indicator:** rework cycles per change; how often the merged diff still matches
  plan.md.

#### Play: Auto mode
- **What changes:** once the plan is approved, Claude applies changes without a prompt for
  each edit. As the guardrails mature (a tuned CLAUDE.md, policy skills, blocking hooks and a
  runnable test suite), auto-accept becomes the default for routine work. Routine means a
  tight spec, a small blast radius and code the tests already cover.
- Review shifts from watching each edit to reviewing artifacts after longer autonomous
  sessions. This is what makes parallel work and closing the loop (Stage 6) possible.

#### Sidebar: legacy systems and the source of truth
For every artifact, name **one** system as the source of truth. Three options:
1. **The repo is the source of truth.** The markdown is authoritative, and Jira and similar
   tools reference the commits. This is the cleanest option for engineering-led
   organisations.
2. **The legacy system is the source of truth.** Jira, ServiceNow or a requirements tool
   holds the record. Claude reads it at the start of a session and writes the outcome back
   through MCP.
3. **Linkage as the minimum bar.** Every artifact notes the record ID, and every record
   notes the commit SHA. This is a good starting point, accepting that there are two
   sources of truth for now.

#### Play: CLAUDE.md
- **What it is:** the context a new joiner would need, covering commands, conventions,
  architecture and "things Claude gets wrong".
- **Execution:** run `/init`, cut it down to day-one essentials, commit it at the repo root,
  and **keep it under a page**.
- **Rule:** "When Claude makes a mistake twice, the correction goes into CLAUDE.md."
- **Prerequisites:** none.
- **Governance:** versioned, reviewed like code, and approved by code owners.
- **Leading indicator:** how often Claude repeats a mistake CLAUDE.md should have caught.
- **Lagging indicator:** time to first merged PR for a new team member.

#### Play: Skills as institutional knowledge
- **Rule of thumb:** write a skill for institutional knowledge that must be applied
  consistently. Don't write one for things that belong in CLAUDE.md or a prompt.
- **Execution:**
  1. Pick one policy that is enforced inconsistently today.
  2. An engineer writes it as SKILL.md from the policy owner's written source of truth.
     Frontmatter says when it triggers; the body says what to do. It can call a check script.
  3. Ship it in `.claude/skills/<name>/` or distribute it through a plugin.
  4. **Test that it triggers** by asking for the task in different ways.
  5. The policy owner signs off every change to the skill.
- **Example:** a `secure-api-review` skill covering authentication, input validation, audit
  events and PII in logs, which runs a check script and includes its output.
- **Prerequisites:** none. A CLAUDE.md helps.
- **Governance:**
  - **A skill is an advisory control.** Nothing forces a session to comply.
  - A policy that must always hold needs something deterministic behind the skill: a hook,
    or a review pass that re-checks the policy at the PR.
  - Skill invocations are logged in session traces.
- **Leading indicator:** time from a policy change being approved to the updated skill
  merging.
- **Lagging indicator:** PR review findings that cite the policy, which should fall toward
  zero. If they don't, either the skill isn't triggering or its text has drifted from the
  policy.

> "The skill makes violations rare and the hook makes them close to impossible."

#### Play: Hooks as build-time guardrails
- **What they do:** block edits to protected paths, run the formatter and linter after
  edits, and keep credentials out of the diff.
- They should back every skill whose policy must hold without exception.
- Keep them **fast and scoped to the changed file**. Heavier checks, like the full test
  suite, belong at the commit or the PR.
- **Hooks that ask a person for approval belong in Deploy, not Build.** An approval prompt
  during the build puts a person back on the critical path of every parallel session.

#### Play: Parallel sessions and subagents
- **Parallel session:** a full Claude Code instance in its own git worktree,
  e.g. `claude --worktree feature-auth`.
- **Subagent:** a scoped helper inside one session, with its own context window and tool
  limits. It suits recurring jobs. Examples: a code simplifier, a **verifier that runs the
  app and checks behaviour against plan.md and reports only**, and a researcher.
- Subagents are defined in `.claude/agents/` and committed to git.
- Start with **two or three sessions**. The ceiling is how many streams one person can
  review properly.
- **Prerequisites:** CLAUDE.md. The Test feedback loop helps.
- **Infrastructure:** git, and permission settings tuned so sessions don't wait on prompts
  for commands the organisation considers safe.
- **Governance:** controls come from repo configuration (hooks and permissions), and session
  activity is attributed to the engineer.
- **Leading indicator:** concurrent sessions per engineer while review quality holds (from
  the OpenTelemetry export); share of time spent steering rather than waiting.
- **Lagging indicator:** changes merged per engineer per week, read alongside the rework rate.

### Stage 4: Test

> "Every session checks its own work before a human sees it, and the configuration that
> steers the agent gets regression-tested like the code it writes."

#### Play: Give Claude a feedback loop
- **What changes:** always give Claude a way to verify its own work, such as tests, a build
  or a screenshot diff. It iterates until the check passes, so what reaches the engineer has
  already passed it.
- This is different from a verifier subagent. The feedback loop runs throughout the task;
  the verifier is a fresh-context final check, so its verdict isn't coloured by the
  assumptions that produced the code.
- **Execution:**
  - Wrap verification in one command, such as `make test`, that exits non-zero on failure.
    List each command in CLAUDE.md with an example of healthy output.
  - Give quantifiable targets, e.g. "all tests in X pass" or "the screenshot matches the mock".
  - **For bug fixes, write the failing test first.** Claude reproduces the bug as a test and
    confirms it fails for the expected reason, and the test is committed. Only then does
    Claude make it pass **without editing the test**, enforced by a hook. A test the agent
    couldn't rewrite is proof the bug is gone.
  - For UI, give Claude a browser or screenshot tool (via MCP) and the mock. Two or three
    rounds is normal.
  - Make verification part of "done": run the tests before reporting completion, and show
    the output.
  - **Protect the loop itself:** an agent fixing code must not be able to weaken the check.
    Use a hook that blocks test-file edits during fix tasks, or reject test changes in review.
- **Prerequisites:** none.
- **Infrastructure:** a test suite and a build that each run with one command; a
  browser or screenshot tool for UI work.
- **Governance:**
  - **Enforced:** verification before "done", and the block on test-file edits during
    fixes, both as hooks where they must be guaranteed.
  - **Evidence:** the literal toolchain output.
  - **Logged:** in the session transcript (OpenTelemetry) and the PR check run.
  - **Approved by:** the code owner, who can concentrate on intent and risk.
- **Leading indicator:** first-pass CI success rate for agent-written changes.
- **Lagging indicator:** review time per PR; change failure rate.

#### Play: Continuous evals in CI
- **Framing:** evals are the **AI-native equivalent of stage-gate QA**. The suite runs
  whenever the agent's configuration changes (model, prompts, CLAUDE.md, skills, hooks) and
  shows whether the agent still works to the same standard.
- It is a **live suite**. As models improve, old cases stop discriminating, and new cases
  come from monitoring.
- **Execution:**
  1. Collect 20–50 real tasks from recent work, with their accepted outcomes.
  2. Write each as a prompt plus acceptance checks: tests pass, lint is clean, behaviour is
     unchanged, policy is followed.
  3. Run non-interactively in CI on a schedule and on every change to CLAUDE.md, skills or
     hooks. The example is a GitHub Actions workflow that loops over `evals/*.json`, calling
     `claude -p` with a restricted `--allowedTools` and a check script.
  4. **Gate configuration changes on the pass rate.**
  5. **Every production incident gets an eval**, written by the owning team, and it stays in
     the suite as a regression test.
- **Prerequisites:** CLAUDE.md and the feedback loop.
- **Infrastructure:** CI that can run Claude Code non-interactively; an API key with budget.
- **Governance:** the pass-rate threshold is a merge check; runs are logged for comparison;
  the team that owns the configuration approves changes. "Evals give QA a gate that keeps up
  with agent output."
- **Leading indicator:** eval pass rate over time; time for an incident to become an eval.
- **Lagging indicator:** regressions caught in CI versus regressions found in production.

### Stage 5: Deploy

> "The agent does everything up to the production gate and nothing past it."

#### Play: AI in the PR review loop
- **What changes:** Claude both reviews incoming PRs against policy and addresses review
  comments on its own PRs. Every PR gets the same review passes, with findings ranked by
  severity. Human review moves up a level, to intent and risk.
- **Execution:**
  - Use either the managed Code Review service or `claude-code-action` in your own CI.
  - The tech lead writes `REVIEW.md` with three passes: **bugs**, **security**, and
    **compliance with spec.md, plan.md and design principles**. It defines what counts as
    Important versus a nit, caps nits (e.g. five per review) and lists what not to report.
  - **Findings don't approve or block a PR on their own. Branch protection still needs a
    code owner.** Severity counts are published in machine-readable form for anyone who
    wants to gate on them.
  - Tagging `@claude` on a comment gets the fix pushed. For Claude's own PRs, it can
    "babysit" the PR to green.
  - A mistake flagged twice in review goes into CLAUDE.md.
  - The tech lead tunes the setup monthly: rating findings and capping nits.
- **Prerequisites:** an updated CLAUDE.md; skills if the review passes enforce written
  policies; defined subagents.
- **Governance:** separation of duties, because **the agent that wrote the code can't
  approve it**. The PR history is the audit record.
- **Leading indicator:** time to first review (should be minutes); share of review comments
  resolved without a human touching the branch.
- **Lagging indicator:** defects and vulnerabilities caught before merge versus those
  escaping to production.

#### Play: Hooks as approval gates
- **What changes:** a hook can **allow, ask or block**. "Ask" pauses the action until a
  named person approves, which is what release gating needs. Hooks run wherever Claude acts:
  for example, blocking migration or infra edits without a change ticket, or blocking test
  edits during a fix.
- **Execution:**
  1. Leadership, change management and compliance list the human gates that must survive.
  2. The platform engineer writes each one as a hook.
  3. Team hooks go in `.claude/settings.json`; non-negotiable ones go in **managed settings**
     that engineers can't switch off.
  4. A block must explain itself and the route to approval.
- **Example:** a PreToolUse hook on Bash that blocks production deploy commands unless a
  release-approval variable is set.
- **Prerequisites:** none.
- **Infrastructure:** a written list of the approvals the change process requires.
- **Worked example, managed settings for a regulated enterprise:**
  - Deny rules for secrets and network tools; an allowlist for the safe inner loop.
  - Bypass mode disabled; only managed permission rules allowed.
  - An OS-level sandbox that is required to start, with no unsandboxed fallback, a domain
    allowlist, and credential file and environment-variable denial.
  - Only managed hooks; side-loading disabled; an approved plugin marketplace only; only
    managed MCP servers; a minimum Claude Code version.
  - Presented as "a starting point to tailor, rather than a recommendation to copy."
- **Leading indicator:** time spent waiting at each gate (hook decisions are in the
  OpenTelemetry export).
- **Lagging indicator:** gate violations reaching production, before versus after hooks.

#### Play: CI/CD integration and deployment
- **Execution:**
  1. **Start with read-only judgment steps:** `claude -p` in the pipeline to **triage a
     failed build, summarise a flaky test** or draft the changelog.
  2. Then **add write steps behind existing gates**, e.g. fixing lint, updating generated
     docs, or addressing review comments. **Everything the agent writes arrives as a PR
     through branch protection, and it has no route to push to main.**
  3. **Sandbox execution:** containers, a network policy, short-lived scoped tokens, and no
     production credentials by default.
  4. **Expose deployment through MCP:** deploy, status and rollback become tools scoped per
     environment, an allowlist rather than a shell script holding credentials.
  5. **Tier autonomy by environment:** in dev the agent deploys freely, staging is in
     between, and in prod the agent prepares the release, a release manager authorises it,
     and a hook enforces the gate.
  6. **Make rollback the most rehearsed path**, a single command that is exercised
     regularly in staging.
- **Example:** a pipeline step that runs on failure. Claude reads the build log, identifies
  the likely cause, says whether it looks flaky or real, and writes a three-line summary for
  the PR.
- **Prerequisites:** Claude in the PR review loop, and hooks as approval gates. "The gates
  must exist before automation accelerates anything through them."
- **Governance:** branch protection; a production deploy hook needing a named release
  manager; every non-interactive run under **the agent's own identity**; permission tiers
  per environment.
- **Leading indicator:** share of pipeline failures triaged without paging a human.
- **Lagging indicator:** DORA measures.

### Stage 6: Maintain

> "The loop closes. A trigger invokes Claude with no person in the invocation path, and
> what it finds re-enters the pipeline as intent.md."

#### Play: Maintenance and closing the loop
- **What changes:**
  - A trigger invokes Claude with no person involved. Triggers include a control-band
    breach, a ticket, a channel message or a schedule.
  - Claude diagnoses, acts only through gated routes, and writes what it finds as intent.md.
  - People triage and review the work; they no longer have to start it.
  - When the whole loop runs headless, **an independent confidence gate sits between
    stages**, either a deterministic check or an adversarial reviewing agent. It decides
    whether the output continues or is escalated to a person.
- **Execution:**
  1. Pick one metric with a stable rolling baseline, e.g. **CI test failure rate**,
     post-deploy 5xx rate or PR cycle time.
  2. **Detection stays deterministic**: mean and standard deviation over a rolling window,
     with Western Electric-style rules. The script is versioned and unit-tested, and no model
     is involved.
  3. Define response tiers in versioned config (`bands.yaml`):
     - **1σ:** log only.
     - **2σ:** invoke Claude **read-only** to diagnose, with tools such as Read, Grep and
       viewing CI runs.
     - **3σ:** Claude may act, but **only by opening a PR into the review gate or triggering
       a pre-approved runbook**.
  4. The trigger is a scheduled workflow, a monitoring webhook or a cron job. Claude runs
     stateless, through `claude -p` in CI or as an Agent SDK service in a sandbox.
  5. The diagnosis is written as an intent.md and flows through the pipeline.
  6. The service owner or on-call engineer triages it: fix now, schedule or dismiss.
     **Dismissals tune the bands.**
  7. When a fix ships, **add an eval for the incident**.
- **Examples:**
  - The CI test failure rate breaches 3σ: the agent **quarantines the flaky test or opens a
    revert PR**, and the review gate decides.
  - The 5xx rate breaches 3σ after a deploy: the agent triggers the existing rollback.
  - PR cycle time drifts: the agent writes a report for leadership.
- **Prerequisites:** the intent.md format; Claude-accelerated PR review; hooks as an action
  boundary; a rollback path.
- **Infrastructure:** a metrics store (e.g. Prometheus or the CI API); repo read access; a
  way to run Claude non-interactively or an Agent SDK service.
- **Governance:** tiers are enforced from versioned config, and permissions and managed
  settings deny production access. Everything is logged with timestamps. The service owner
  approves findings, and runbooks are pre-approved.
- **Leading indicator:** time from breach to an intent.md in the triage queue.
- **Lagging indicator:** share of findings that become merged fixes; repeat incidents of the
  same class, which should fall as evals accumulate.

#### Play: Recurring codebase scans (Claude Security)
- **What changes:** a scan goes stale on both sides: the code changes, and newer models find
  vulnerabilities older ones missed. Scans therefore run on a schedule with no human
  starting them, and findings go through the same gates as any other change.
- **Claude Security** is the hosted form, in public beta for Claude Enterprise. Each finding
  is validated before it is reported and carries a confidence rating. Suggested patches are
  reviewed in Claude Code on the web.
- **Execution:**
  1. Connect repos and organise them into projects with clear owners.
  2. Run a baseline full scan of critical repos, even ones scanned before.
  3. Scan weekly by default.
  4. Triage with the confidence rating. **Dismiss with a reason** so a finding doesn't
     return as new.
  5. A bounded fix goes through the PR review gate; anything wider becomes an intent.md.
  6. Add an eval for each vulnerability class once fixed.
  7. Export findings or use webhooks to keep the existing tracker as the system of record.
- **Prerequisites:** the PR review gate, hooks as approval gates, and the intent.md format.
- **Infrastructure:** the Anthropic GitHub App, Claude Code on the web, Extra Usage with a
  spend limit, premium seats for people who run scans, and an admin enabling the feature.
  Scans bill on consumption.
- **Governance:** central admin controls; validation and confidence on every finding;
  reasons on dismissals. It **augments** static analysis and dependency scanning, which stay
  as deterministic checks in CI.
- **Leading indicator:** share of repos on a schedule; time from finding to patch entering
  review.
- **Lagging indicator:** vulnerabilities found by scheduled scans versus in production or by
  external report; findings per scan on repos with several runs, which should trend down.

#### Play: Claude on call with Claude Tag
- Claude Tag (public beta, Slack) makes Claude a member of incident channels under its own
  identity, as a first responder.
- Anyone in the channel can guide it. Using MCP, it verifies that metrics are back at
  baseline and writes the post-mortem to a version-controlled lessons file.
- When tagged on a ticket or asked in a channel, it triages: **a small, bounded fix arrives
  as a PR through the review gate, and anything larger becomes an intent.md.**
- The channel is the audit trail: request, diagnosis, human authorisation and fix.

**Then:**

| Play | Needs first |

## 6. Recurring principles

1. **Commit an artifact at every stage**; the chain of commits is the audit trail.
2. **Prompt each step by hand first**, then automate the triggers.
3. **People are accountable for judgment calls**, and their attention concentrates at the
   gates.
4. **Skills are advisory; hooks are deterministic.** Back any must-hold policy with a hook or
   a re-check at the PR.
5. **Keep approval prompts out of the build critical path.** Gates that ask a person belong
   at Deploy.
6. **Separation of duties:** the agent that wrote the code can't approve it, and branch
   protection needs a code owner.
7. **Start read-only, then add write steps behind existing gates.** Agent writes always
   arrive as PRs.
8. **Agents act up to the production gate and can't pass it.** Autonomy is tiered by
   environment.
9. **Detection is deterministic; diagnosis is the model's job.** What Claude may do is set
   by tier.
10. **Every incident becomes an eval**, and the eval suite is live and evolving.
11. **One source of truth per artifact**, or at least linkage between systems.
12. **Measure every play** with a leading and a lagging indicator, mostly read from git, PR
    metadata, CI logs and OpenTelemetry.

## 7. What the playbook doesn't cover

- No maturity model or scored levels. It describes a range between traditional and AI-native.
- No numeric targets, apart from directional statements (e.g. weeks to hours, minutes,
  toward zero).
- No dedicated QA or QE role model, test-case management process, or defect-tracker workflow.
  Testing is framed as feedback loops, evals, review passes and incident-driven evals.
- No "self-healing" by that name. The closest are the Maintain tiers (quarantine a flaky test
  or open a revert PR at 3σ) and the rule that fixes must not edit tests.
- No user stories. intent.md replaces the user story, story points and refinement path.
- Security detail is deferred to the companion guide.
